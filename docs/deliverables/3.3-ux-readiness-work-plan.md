## 1. Objective

Leave the application ready for public mainnet launch from the user-experience side. When
this deliverable closes, a Spanish-speaking user with no prior Stellar experience must be
able to complete their first deposit without meeting English text, unhandled errors or
usability problems on mobile.

## 2. Context

Vaquita targets LATAM users who arrive through Anclap (ARS/USD) and who will mostly use
the app from a phone. That is why this deliverable prioritises three things: Spanish as a
first-class experience rather than a partial translation, robustness against errors (new
users abandon at the first silent failure), and real mobile verification on physical
devices, not emulators.

One point conditions the whole scope: **"empty wallet" does not mean a single thing in
Vaquita**. Account creation is delegated to Pollar, whose login modal offers three ways in,
and each produces a different onboarding
(`apps/web/src/components/providers/Providers.tsx`):

| Way in | What it is | What changes in onboarding |
|---|---|---|
| Own wallet | Freighter, Albedo, xBull, Lobstr and the rest of the kit's modules. The user signs in their wallet's own UI | Requires the extension installed; there is a signing popup; withdrawal returns to the wallet that signed |
| Social login | Sign-up with Google or email, nothing to install | No extension and no signing popup; withdrawal asks for a destination address. This is the expected path for the new LATAM user |
| Passkey | Smart account with WebAuthn (a `C…` address) | Biometric prompt; rejection arrives as `NotAllowedError` / `AbortError` |

In all three, Vaquita is **non-custodial**: funds live in the contracts and the app never
takes or stores the user's keys or money. What changes is the signing surface, and with it
the error states and the copy that has to be covered.

The screen recording required by the SCF criterion is made on the social-login path, which
represents the target user with no prior Stellar experience, and mentions the own-wallet
path as the alternative.

## 5. Work breakdown

### 5.1 Spanish onboarding

**Register decided: neutral *tuteo*** ("puedes", "toca", "agrega"), not *voseo*. The
audience is LATAM as a whole, not only Argentina. All new or corrected copy is written this
way, and existing *voseo* copy is migrated.

- [ ] Full flow from a new account to the first active deposit, 100 % in Spanish, via social login and verified with an own wallet (Freighter) as well
- [ ] String audit: zero hardcoded English text on user-facing screens (the 78 components that do not import `useTranslation` today are the starting point)
- [ ] Migration to neutral *tuteo* of the 18 *voseo* strings in `es.json`, starting with `onboarding.install.*`, where both registers coexist on the same screen today
- [ ] Reviewed copy for KYC, deposit, early withdrawal, completed cycle and rewards
- [ ] Tooltips and contextual help at the friction steps (choice of entry method, transaction signing, period selection)
- [ ] Confirmation and success texts consistent in tone with the rest of the product
- [ ] First anonymous render: a device with `navigator.language` set to Spanish enters in Spanish without a profile, and `<html lang>` ends up as `es`
- [ ] The language selector is reachable before login, not only from profile preferences
- [ ] Key parity across `en`, `es` and `pt` when the deliverable closes (today the only automated parity test, `i18n/badge-keys.test.ts`, covers only `achievements.items`; extending it to the full dictionary closes the hole permanently)

### 5.2 Error handling

Critical paths covered:

| Path | Errors to handle | Expected behaviour |
|---|---|---|
| Sign-up / account connection | Wallet not installed, connection rejected, wrong network | Clear message + install link. The network is fixed at build time (`getStellarNetwork()`); **there is no in-app network switch**, so the message must say which network to select in the wallet rather than offer to change it |
| Deposit | Insufficient funds, missing USDC trustline, rejected signature, RPC timeout | Cause-specific message + retry without losing the form — **except** when the transaction already reached the network (see below) |
| Early withdrawal | Rejected signature, transaction failure | Explicit confirmation that accrued interest is forfeited **before** signing, retry available |
| Completed cycle / claim | Distribution failure, timeout | Visible transaction state, retry, and the hash linked to the explorer for support |
| Data loading (APY, pools, leaderboard) | RPC down, slow response | Skeletons / loading states, retry message, never a blank screen |

**Pending transaction — do not offer retry.** `humanizeTxError` distinguishes a real failure
from the case where the transaction was already submitted and is still confirming: it
returns `pending: true` alongside the `hash`. That signal does not reach the screen today.
`ErrorNotice.tsx` destructures only `title` and discards `pending`/`hash`, and
`DepositModal/DepositMethodModal.tsx` turns the CTA into "Retry" on any error, the pending
one included; pressing it fires a second deposit while the first can still confirm. Closing
this deliverable includes propagating `pending` and `hash` through to the UI and, in that
state, showing the hash, asking the user to check their balance, and **not** rendering the
retry, across all five paths. The same applies to timeouts, which can arrive from before or
after submission.

Cross-cutting criteria:

- [ ] Zero unhandled errors across the five paths in the table, in the console and in the QA report
- [ ] No silent failures: every operation that fails communicates what happened and what to do
- [ ] Signature errors or rejections neither break the flow nor lose the user's state
- [ ] No message shows the raw error text to the user (`raw` is for telemetry and for a "see details" button)
- [ ] No screen offers to retry a transaction that already reached the network
- [ ] Every `txError.ts` message resolves by key in all three locales; the inline English fallback is never seen in the app

### 5.3 FAQ

The public FAQ is already live at **https://www.vaquita.fi/#faq**, reachable without a
session, and the in-app help centre complements it from the profile. SCF criterion 3 is
covered by that URL. The remaining work is accuracy and coverage, not publication.

**Accuracy — fix before closing.** The public answer about early withdrawal currently says
the user merely misses the bonus for completing the goal. The contract does something more
severe: withdrawing before maturity transfers **principal only**, and all accrued interest
is forfeited — part of it (`early_withdrawal_fee`, in basis points, capped at 20 %) goes to
protocol fees and the rest stays in the period's reward pool, shared among those who do
complete their cycle (`contracts/vaquita-pool/src/lib.rs`). A user who reads the current
version and withdraws early receives less than they expected.

- [ ] Rewrite the early-withdrawal answer to say that principal returns in full and accrued interest is forfeited
- [ ] Align the same text in the in-app help centre, whose current answer ("withdrawing before the term is not available in this version") does not match what the contract allows either

**Coverage — topics to add.** The public FAQ answers four entry-level questions today (does
one need to know crypto, how much to start with, what happens if I need the money earlier,
how it generates interest). Missing are the ones a new user asks right before depositing:

- [ ] Which lock periods exist. On mainnet, Vaquita's launch policy is **1 month, 3 months and 6 months** (testnet runs shorter values so full cycles can be tested). The set is configurable on-chain (`add_lock_period` / `remove_lock_period`) and the app reads it from `token.lockPeriods`, so the FAQ must be worded so that adding or removing a period does not leave it stale, and verified against the deployment before closing
- [ ] How rewards are calculated and distributed (pro-rata over the period's pool on completing the goal)
- [ ] Where the yield comes from (Blend Capital, DeFindex), rather than "real yield" with no source
- [ ] Ways in: social login (Google/email), passkey, or an own wallet — Freighter, Albedo, xBull, Lobstr and the rest of the Stellar Wallets Kit modules the Pollar modal exposes. Ledger, Trezor and WalletConnect are not enabled
- [ ] Which network the app runs on and why there is no network selector
- [ ] How to deposit from ARS/USD (Anclap SEP-24 flow and KYC)
- [ ] Security: Vaquita is non-custodial. Funds live in the contracts, only the user moves them, and the app never sees or stores private keys. The contracts that hold them are listed
- [ ] Support: where to report problems. The in-app help centre points to hello@vaquita.finance; unify with the public channel (Telegram / GitHub issues) or the user gets two different answers to the same question

**Language and consistency:**

- [ ] Spanish version of the public FAQ verified end to end with the landing page's language selector
- [ ] A single source of truth between the public FAQ and the in-app help centre: same answers, no texts that contradict each other
- [ ] FAQ link reachable from the app and from the login screen, not only from the landing page

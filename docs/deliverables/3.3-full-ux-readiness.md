## 2. What "empty wallet" means here

Account creation is delegated to Pollar, whose login modal offers three ways in
(`apps/web/src/components/providers/Providers.tsx`). Each produces a different onboarding,
so the criterion's "empty wallet" resolves to three different starting points:

| Way in | What it is | What changes in onboarding |
|---|---|---|
| Own wallet | Freighter, Albedo, xBull, Lobstr and the rest of the kit's modules; the user signs in their wallet's own UI | Requires the extension; there is a signing popup; withdrawal returns to the wallet that signed |
| Social login | Sign-up with Google or email, nothing to install | No extension and no signing popup; withdrawal asks for a destination address. The expected path for a new LATAM user |
| Passkey | Smart account with WebAuthn (a `C…` address) | Biometric prompt; rejection arrives as `NotAllowedError` / `AbortError` |

In all three, Vaquita is **non-custodial**: funds live in the contracts and the app never
takes or stores the user's keys or money. What changes is the signing surface, and with it
the error states and the copy that has to be covered.

## 4. Error handling

Five critical paths carry the criterion's "zero unhandled errors": account connection,
deposit, early withdrawal, completed cycle / claim, and data loading. The expected
behaviour for each failure is specified in the work plan §5.2.

The transaction error mapping itself is implemented in
`apps/web/src/core-ui/helpers/txError.ts`, covering rejected signature,
`Error(Contract, #10/#13)`, trustline, balance, network, timeout and pending transaction.
Its unit tests run in Web CI — see [`../testing.md`](../testing.md).
